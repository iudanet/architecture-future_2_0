# Обоснование конфигурации

Конфигурация разворачивает типовую среду домена в Yandex Cloud:
- сеть;
- bastion для администрирования;
- ВМ приложения с диском данных в приватной подсети.

По этому шаблону каждый домен получает изолированную среду: Клиники, Финтех, ИИ, партнёры.

## Ресурсы и параметры

| Ресурс | Параметры | Почему так |
|---|---|---|
| `yandex_vpc_network` `future20-net` | Отдельная сеть на среду | Изоляция домена от других сред и от прочих ресурсов каталога |
| `yandex_vpc_subnet` public / private | `10.20.1.0/24` в `ru-central1-a`, `10.20.2.0/24` в `ru-central1-d` | В публичной подсети только bastion; приложение и данные без публичных адресов. /24 оставляет запас на рост. Разные зоны — из-за квоты тестового облака (2 vCPU на зону). По умолчанию (`variables.tf`) обе подсети в одной зоне; в проде отказоустойчивость дают дублирование ВМ по зонам и managed-сервисы |
| `yandex_vpc_gateway` + `yandex_vpc_route_table` | Shared egress NAT, маршрут `0.0.0.0/0` для private | ВМ без публичного IP получают исходящий доступ (обновления, пакеты, внешние API) и недоступны снаружи. Управляемый NAT-шлюз вместо NAT-инстанса: не нужно сопровождать ВМ |
| `yandex_vpc_security_group` bastion | SSH 22 только из `admin_cidrs` | Единая точка входа. `0.0.0.0/0` запрещён валидацией переменной |
| `yandex_vpc_security_group` app | SSH только из SG bastion, 443 только из приватной подсети | Приложение доступно только сервисам среды |
| `yandex_compute_instance` bastion | `standard-v3`, 2 vCPU 20%, 2 ГБ, HDD 15 ГБ | Нагрузка — только SSH-прокси. 2 vCPU — минимум для `standard-v3`, а доля 20% снижает стоимость |
| `yandex_compute_instance` app | `standard-v3`, 2 vCPU 50%, 4 ГБ, HDD 15 ГБ | Минимальный размер для доменного ETL или API |
| `yandex_compute_disk` data | SSD 10 ГБ, отдельный ресурс | Данные отделены от загрузочного диска: ВМ можно пересоздать без потери данных, диск — увеличить или снять снапшот (`data_disk_id` в outputs) |
| `preemptible = true`, загрузочные диски `network-hdd` | Значения в `terraform.tfvars` | Тестовая среда дешевле и укладывается в квоты облака (2 vCPU, 20 ГБ HDD и 10 ГБ SSD на зону). В проде — `false` (значение по умолчанию), `network-ssd`, размеры по нагрузке |

Дополнительные решения:
- **Образ** берётся по семейству `ubuntu-2204-lts`. Выход нового образа не пересоздаёт работающие ВМ: `lifecycle.ignore_changes` на `image_id`.
- **Размеры ВМ** меняются переменными без пересоздания: `allow_stopping_for_update`.
- **Метки** `project` и `managed-by=terraform` стоят на всех ресурсах.
- **Секреты:** токен, облако и каталог читаются из окружения (`YC_TOKEN`, `YC_CLOUD_ID`, `YC_FOLDER_ID`) и в репозиторий не попадают.

## Почему декларативный подход

- **Описывается целевое состояние, а не шаги.** Terraform сам вычисляет порядок по зависимостям: сеть и NAT-шлюз создаются параллельно, затем таблица маршрутов, подсети, группы безопасности, диск, ВМ. Разницу с текущим состоянием показывает `plan`.
- **Идемпотентность:** повторный `apply` без изменений ничего не меняет, дрейф виден в `plan`.
- **Ревью изменений:** конфигурация лежит в Git, переменные проверяются валидацией до обращения к облаку.

## Как IaC обеспечивает воспроизводимость и масштабируемость

- **Воспроизводимость.**
  - Одна конфигурация даёт одинаковые среды dev, test, prod и среды доменов; отличается только `terraform.tfvars`.
  - Версия провайдера зафиксирована в `.terraform.lock.hcl`.
  - Удалённую среду можно восстановить командой `apply`.
- **Масштабируемость.**
  - Новый домен или партнёр подключается своим `tfvars` с другими `prefix` и CIDR.
  - Размеры ВМ и дисков задаются переменными.
  - Следующий шаг — вынести шаблон в модуль и вызывать его для каждого домена.
- **Контроль.** История изменений хранится в Git. В проде state хранится в Object Storage — блок `backend "s3"` в `main.tf`.
