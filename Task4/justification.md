# Обоснование конфигурации

Конфигурация разворачивает типовую среду домена в Yandex Cloud: сеть, bastion для администрирования и ВМ приложения с диском данных в приватной подсети. По этому шаблону каждый домен получает свою изолированную среду: Клиники, Финтех, ИИ, партнёры.

## Ресурсы и параметры

| Ресурс | Параметры | Почему так |
|---|---|---|
| `yandex_vpc_network` `future20-net` | Отдельная сеть на среду | Изоляция домена от других сред и от существующих ресурсов каталога |
| `yandex_vpc_subnet` public / private | `10.20.1.0/24` в `ru-central1-a`, `10.20.2.0/24` в `ru-central1-d` | В публичной подсети только bastion; приложения и данные без публичных адресов. Подсети в разных зонах: отказ одной зоны не лишает доступа ко всей среде. /24 даёт запас на рост |
| `yandex_vpc_gateway` + `yandex_vpc_route_table` | Shared egress NAT, маршрут `0.0.0.0/0` для private | ВМ без публичного IP получают исходящий доступ (обновления, пакеты, внешние API), но недоступны снаружи. Управляемый NAT-шлюз вместо NAT-инстанса: не нужно сопровождать ВМ |
| `yandex_vpc_security_group` bastion | SSH 22 только из `admin_cidrs` | Единая контролируемая точка входа. В проде список — адреса офиса или VPN |
| `yandex_vpc_security_group` app | SSH только из SG bastion, 443 внутри VPC | Приложение доступно только из сети среды |
| `yandex_compute_instance` bastion | 2 vCPU 20%, 2 ГБ, HDD 15 ГБ | Нагрузка — только SSH-прокси, гарантированная доля CPU 20% минимизирует стоимость |
| `yandex_compute_instance` app | 2 vCPU 50%, 4 ГБ, HDD 15 ГБ | Минимальный размер для сервиса доменного ETL или API. В проде загрузочный диск — `network-ssd` |
| `yandex_compute_disk` data | SSD 10 ГБ, отдельный ресурс | Данные отделены от загрузочного диска: ВМ можно пересоздать без потери данных, диск — увеличить или снять снапшот |
| `preemptible = true`, загрузочные диски `network-hdd` | Прерываемые ВМ, HDD | Тестовая среда дешевле и укладывается в квоты облака (2 vCPU, 20 ГБ HDD и 10 ГБ SSD на зону). В проде — `false`, `network-ssd`, размеры по нагрузке |

Образ берётся по семейству `ubuntu-2204-lts`, поэтому при каждом создании используется актуальный образ. Все ресурсы помечены метками `project` и `managed-by=terraform`. Префикс `future20` отделяет их от ресурсов каталога, которыми Terraform не управляет.

Токен, облако и каталог не хранятся в коде: провайдер читает `YC_TOKEN`, `YC_CLOUD_ID` и `YC_FOLDER_ID` из окружения.

## Почему декларативный подход

- **Описывается целевое состояние, а не шаги.** Terraform сам вычисляет порядок по зависимостям (сеть → NAT → таблица маршрутов → подсеть → SG → ВМ) и разницу с текущим состоянием (`plan`).
- **Идемпотентность:** повторный `apply` без изменений ничего не меняет, дрейф виден в `plan`.
- **Изменения проходят ревью:** конфигурация лежит в Git, `plan` прикладывается к PR.

## Как IaC обеспечивает воспроизводимость и масштабируемость

- **Воспроизводимость.** Одна конфигурация даёт одинаковые среды: dev, test, prod и среды доменов. Отличаются они только `terraform.tfvars`. Удалённую среду можно восстановить командой `apply`.
- **Масштабируемость.** Новый домен или партнёр подключается копированием `tfvars` с другим `prefix` и CIDR — без ручной настройки. Размеры ВМ и дисков меняются переменными. Дальше шаблон выносится в модуль и вызывается для каждого домена.
- **Контроль и аудит.** История изменений инфраструктуры хранится в Git, а state фиксирует фактическое состояние. В проде state хранится в Object Storage с блокировками.

## Что развёртывается вручную

Облако, платёжный аккаунт, каталог, квоты, сервисный аккаунт или токен, профиль `yc`, SSH-ключ, бакет для state и DNS-зона. Это разовая подготовка платформы, она выполняется до Terraform (см. [diagram.png](./diagram.png)).

## Проверка

```bash
export YC_TOKEN=$(yc iam create-token) YC_CLOUD_ID=$(yc config get cloud-id) YC_FOLDER_ID=<каталог>
terraform init && terraform plan && terraform apply
```
